# SoloOS v0.1.0 — Target, Core Story & Five-Pillar Completion

## 0. Purpose of this document

SoloOS already has a working spine (Entry → Event → Project → Review across five
pillars; Node/TS + SQLite server, Vite + React web, `solo capture` CLI, GitHub
ingestion, an agent-cost ledger). This is **not** a greenfield spec. It is a
**strategic sharpening** that locks, for the v0.1.0 cycle:

1. the primary target user,
2. the single core user story,
3. completion of all five pillars (the real build work), and
4. the connection topology (local-first now, hosted client architected-for).

It is the source of truth the implementation plan is derived from.

---

## 1. Target user (v0.1.0)

**You, the builder — running your own one-person company. User #1, dogfood-first,
fully local.**

Other audiences from `brainstorming.md` (indie devs broadly; AI-heavy solo devs)
are **not excluded long-term** — they are simply not who v0.1.0 optimizes for.
Optimizing for user #1 gives the fastest, most honest feedback loop and fits the
local-first, no-cloud design.

---

## 2. Core user story (the spine)

> One-line capture from the terminal → auto-attributed to a **project** + one of
> **five pillars** → surfaced as a five-axis **balance** on the Cockpit → a
> **mandatory weekly Review Gate** that blocks the Cockpit until you reflect.

**Hard requirement for v0.1.0:** all five pillars are *clearly defined and
actually fed* — no placeholder axes. The radar must be honest on all five.

---

## 3. The five-pillar model

Each pillar is one axis on the Cockpit radar. The defining insight:

> **Four pillars are *flows* (activity / throughput within a period). Energy is a
> *level* (operator state).** They render on the same 0–100 axis but are computed
> differently.

| Pillar | Class | What an "event" is | Source in v0.1.0 | Value | Status |
|---|---|---|---|---|---|
| **Input** | flow | a learning / idea / todo capture | manual `solo capture` → classified `INPUT` | impact weight (default 1) | ✅ exists |
| **Output** | flow | a commit / shipped deliverable | GitHub webhook (commits) | impact per commit | ✅ exists |
| **Financial** | flow | revenue or AI-spend movement | agent-cost ledger (spend) auto + manual revenue | signed net (rev − spend) | ✅ exists |
| **Audience** | flow | a star / watcher / fork / follower gain **or** a manual touch (meeting / post / outreach) | **GitHub-social poller (delta) auto + manual capture** | delta count / touch weight | 🔨 build |
| **Energy** | **state** | a self-rating of operator state | **`solo energy <1–5>` + required rating at the weekly Review** | the rating value (level) | 🔨 build |

The type layer already supports all five
(`packages/shared/src/types/pillar.ts`: `PILLARS = ['INPUT','OUTPUT','AUDIENCE',
'FINANCIAL','ENERGY']`) and `PillarSnapshot` already carries
`{ pillar, event_count, impact_sum, score }`
(`packages/shared/src/types/review.ts`). The v0.1.0 gap is purely **ingestion +
scoring for Energy and Audience**, plus a defined per-class `score` computation.

### 3.1 Radar normalization (the one genuine design choice)

- **Chosen:** each axis → **0–100 within the review period, relative to that
  pillar's own rolling baseline** (flow pillars) or rating scale (Energy). The
  radar answers *"where am I above / below my own normal?"* — directly serving the
  documented use case: *"is the stress from cash, or from not resting?"*
- **Rejected:** raw absolute scores. Dollars, commit-counts, and a 1–5 rating do
  not share a scale, so the radar becomes unreadable.

`PillarSnapshot`'s existing `{ event_count, impact_sum, score }` shape is kept;
v0.1.0 defines how `score` is derived per class:
- **Flow pillars:** `score` = `impact_sum` for the period normalized to 0–100
  against the pillar's **trailing rolling max** over a fixed window (default: the
  last 8 periods; the constant is tunable). 100 = your recent peak for that pillar;
  the axis reads "current activity vs my own recent best." Financial uses signed
  net throughput, so a period where spend exceeds revenue reads low on the axis.
- **Energy (state):** `score` = mean self-rating in the period, scaled 1–5 → 0–100.
  `event_count` = number of readings; `impact_sum` is not meaningful for Energy
  and is set to the rating sum (kept only for shape compatibility).

### 3.2 Energy — specification

- **CLI:** `solo energy <1–5>` records an Energy reading (an `Entry` →
  `Event{ pillar: ENERGY, impact: rating }`).
- **Review Gate:** completing the weekly review **requires** an Energy rating for
  the period (a slider/quick input in the gate). Reflection text is still required
  as today. This is the "light structured check-in" that keeps the hardest pillar
  honest by riding the ritual you already cannot skip.
- **Scoring:** level, per §3.1.

### 3.3 Audience — specification

- **Auto (GitHub-social poller):** reuse the existing GitHub integration to
  snapshot stars / watchers / forks / followers on linked repos; the **delta**
  since the last snapshot becomes Audience events (e.g. `+3 stars on repo X`,
  impact = delta count).
- **Manual:** `solo capture` can be routed to the `AUDIENCE` pillar for offline
  touches (meeting, post, outreach), impact = touch weight (default 1).
- **Scoring:** flow, per §3.1.

### 3.4 How this reinforces the loop

The weekly Review Gate already blocks the Cockpit and already integrates the
agent-cost (Financial) summary with continue / pause / kill / double_down
decisions. v0.1.0 extends the same gate to capture the **Energy rating** (and,
optionally, an Audience snapshot number), so the two hard pillars stay populated
through the mandatory ritual rather than through fragile external automation.

## 4. Connection topology

Both data paths keep **all data in local SQLite** (`~/.soloos/soloos.db`). The
only difference between modes is *where the UI is served from* and *how it reaches
the local API*.

- **Mode 2 — fully local (SHIPS in v0.1.0):** server + Vite client both run on the
  user's machine (`pnpm dev`). This is what user #1 dogfoods.
- **Mode 1 — hosted UI, local data (ARCHITECTED-FOR, ships v0.1.x):** a web client
  hosted on Vercel (e.g. `soloos.vercel.app`) that connects to the `solo` server
  running on the user's machine. GitNexus-style "zero-install client, bring your
  own local server." Data never leaves localhost.

### 4.1 The seam (two edits make Mode 1 zero-rework)

| Edit | File | From → To | Local behavior |
|---|---|---|---|
| Server CORS | `apps/server/src/index.ts:33` | hardcoded origin array → env-driven allowlist (default = today's localhost origins; extra origins via `SOLOOS_ALLOWED_ORIGINS`) | unchanged |
| Client API base | `apps/web/src/lib/api.ts:12` | `const BASE = '/api'` → `import.meta.env.VITE_API_BASE ?? '/api'` | unchanged (same-origin Vite proxy) |

Current hardcoded CORS origins to preserve as the default:
`http://localhost:5173`, `http://127.0.0.1:5173`, `http://[::1]:5173`.

### 4.2 Mode 1 wiring (documented for v0.1.x — NOT built in v0.1.0)

1. Deploy the client to Vercel.
2. User runs the local `solo` server.
3. Hosted client sets `VITE_API_BASE=http://localhost:3000`.
4. Server adds the Vercel origin to `SOLOOS_ALLOWED_ORIGINS`.
5. Relies on the browser secure-context exception that treats `localhost` /
   `127.0.0.1` as a trustworthy origin for an HTTPS page.
6. A pairing/port step + secure-context handling beyond the config seam is part of
   the Mode 1 work, **not** v0.1.0.

## 5. v0.1.0 scope boundary

**In scope (the build):**
1. Energy pillar — `solo energy <1–5>` CLI + Entry/Event ingestion; required
   rating in the Review Gate; `score` as a level.
2. Audience pillar — GitHub-social poller (deltas → Audience events) + manual
   capture routable to `AUDIENCE`; `score` as a flow.
3. Radar scoring — per-pillar `score` computation (flow normalized vs baseline;
   Energy as level) so the Cockpit renders all five honestly.
4. Connection seam — CORS + client API-base made config-driven (Mode-1-ready, not
   deployed).
5. End-to-end loop — capture → classify → Cockpit (5 axes) → Review Gate, tested.

**Explicitly out of scope (named so they don't creep in):**
- Actual Vercel deploy of the hosted client → v0.1.x.
- Multi-platform Audience connectors (X/Twitter, newsletter) → later.
- Energy *proxy* signals (late-night commits, burn-as-heat) → later.
- Multi-user / auth / sharing.
- Pairing token + secure-context handling beyond the config seam → ships with
  Mode 1.

## 6. Success criteria (v0.1.0 done =)

- [ ] `solo energy 3` records a reading → visible in the DB and on the radar.
- [ ] The weekly Review Gate **requires** an Energy rating to complete (reflection
      still required).
- [ ] GitHub-social deltas create Audience events; manual capture can target
      `AUDIENCE`.
- [ ] The Cockpit radar shows **all five axes with real (non-placeholder) data**,
      normalized 0–100 per the flow-vs-level rules.
- [ ] The capture → Cockpit → Review loop runs end-to-end; the server Vitest suite
      is green.
- [ ] CORS allowlist + client API base are config-driven; `pnpm dev` behaves
      identically (no local regression).
- [ ] Mode 1 (hosted Vercel client) is documented as the next-step seam, not
      shipped.
